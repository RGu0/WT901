`0x64` / `0x69` **只在指令小节里，那张地址表漏了它们**。逐项落位见 §5.1 与 §5.2，

全为零（§10）。「这批器件没烧写序列号」与「本型号根本没有这个寄存器、读未定义地址
返回零」两种解释目前分不开，`ray-309` scope 2 用实测定论（读官方标为保留/未定义的
地址与它比对）。在那之前，**不要把 `0x7F` 当成已核实的寄存器**。

带「真机实测」标注的条目另有本仓库的实测数据支撑，证据路径见各节末尾。**真机实测与
上游资料冲突时以实测为准**——`0x0A` 就是这么被排除的：通用编码表标它 125 Hz，实测
99.29 Hz（§6、§9 第 5 条）。

（`0x71` 的寄存器个数不算这类冲突：手册摘要一直写着 8，是本库自己读成了 4，见 §3。）

⚠ **本文档记录的是设备与协议的事实，不是本库的 API。** API 见
[README](../README.md) 与 `wt901` 命名空间。

## 1. 器件能力（官方规格书）

| 项 | 指标 |
|---|---|
| 加速度量程 / 分辨率 | ±16 g / 0.0005 g·LSB⁻¹ |
| 角速度量程 / 分辨率 | ±2000 °/s / 0.061 (°/s)·LSB⁻¹ |
| 磁场量程 / 分辨率 | ±2 Gauss / 0.0667 mGauss·LSB⁻¹ |
| 内部采样率 | 1 kHz |
| 传感器带宽 | 5–256 Hz |
| 姿态精度 | 0.2°（俯仰/横滚）；航向 9 轴 1°、6 轴静态 0.5° |
| 角度量程 | Roll ±180°，Pitch ±90°，Yaw ±180° |
| 输出速率 | 0.2–200 Hz，**默认 10 Hz**；50 Hz 以上为打包传输 |
| 无线 | BLE 5.0，标称最大 90 m |
| 功耗 | 工作 ≈4.5 mA，待机 14–16 µA |

**两条影响实现的事实**：默认 10 Hz 远低于步态分析所需，连接后必须主动配置；
50 Hz 以上一次 BLE 通知可能携带多帧，**解析器不能假设「一次通知 = 一帧」**。

### 1.1 坐标系与欧拉角旋转顺序

协议文档写明了，本库此前**一条都没记**——而这几条决定了角度数据该怎么读。

**坐标系：东北天。** 模块正方向放置时，**向左为 X 轴、向前为 Y 轴、向上为 Z 轴**。
上行帧里的 `Roll` / `Pitch` / `Yaw` 分别是绕 X / Y / Z 轴的角度。

**欧拉角旋转顺序：Z-Y-X**，即先绕 Z 轴转，再绕 Y 轴转，最后绕 X 轴转。

### 1.2 俯仰角 ±90° 会折回，而且三轴耦合——这不是设备故障

§1 的规格表记了「Pitch ±90°」这个**量程**，但没记它的**含义**。协议文档原文说了两件
事，两件都会被下游当成 bug 去查：

1. **俯仰角超过 90° 会折回。** 横滚角的范围虽然是 ±180°，但因为旋转顺序是 Z-Y-X，
   表示姿态时俯仰角（Y 轴）的范围**只有 ±90°**；超过 90° 后会变换到小于 90°，
   **同时让 X 轴的角度大于 180°**。
2. **三轴是耦合的。** 只有小角度时三轴才表现出独立变化；大角度时姿态角耦合变化——
   比如 **Y 轴接近 90° 时，即使姿态只绕 Y 轴转动，X 轴的角度也会跟着大幅变化**。

**这是欧拉角表示姿态的固有特性，不是设备故障，也不是本库的解码错误。** 不把它写
下来，下一个人看到「只绕一个轴转，另一个轴的读数却在跳」会去查链路、查解码、查
标定——那三处都没有问题。

需要在大俯仰角下工作的下游应当用四元数（`0x51`–`0x54`，见 §5.1）而不是欧拉角；
本库的 `Telemetry.read_quaternion()` 就是给这种场合的。

> ⚠ **本库没有实测过这两条**，它们是协议文档的转述。转述不必先实测，但也不该被当成
> 本库量到过的事实——与 `Bandwidth` 那七个标称值同一种证据强度（§0）。

## 3. 上行帧格式

固定 **20 字节**：`0x55 | Flag | 18 字节负载`。**协议无校验和**——这与串口的
11 字节 0x55 协议不同，帧同步只能靠头字节与标志位约束。

### Flag `0x61` — 实时数据帧（默认持续上报）

负载为 9 个 int16（小端），顺序 AX AY AZ / WX WY WZ / Roll Pitch Yaw。
器件原始语义：

```
a[i]     = raw / 32768 * 16     (g)
w[i]     = raw / 32768 * 2000   (°/s)
angle[i] = raw / 32768 * 180    (°)
```

本库对外统一为 SI，换算集中在 `wt901.protocol.units` 一处。

> ⚠ **官方协议文档的复制粘贴错误**：WY 与 WZ 的公式都被误写为
> `(WXH<<8)|WXL`。三个轴各取各自的字节，不要照抄文档。

### Flag `0x61` — 位移帧（寄存器 `0x96` 置 1 后替代上表）

同样的 Flag，负载语义改为位移 XYZ / 位移速度 XYZ / 角度 XYZ，位移单位 mm。

> ⚠ **协议陷阱**：位移帧与实时数据帧**共用 Flag `0x61`，字节布局无法区分**。
> 解析必须以「当前已知的 `0x96` 配置状态」为上下文。本库的选择是拒绝而非猜测：
> `OutputMode` 非 `MOTION` 时 `samples()` 直接抛 `ConfigurationError`。

### Flag `0x71` — 寄存器回读帧

由主动读寄存器指令触发。`byte[2..3]` 是起始寄存器地址（小端），`byte[4..19]` 是
从该地址起**连续 8 个**寄存器值（int16 小端）。所以读 `0x3A` 一次拿到 HX/HY/HZ，
读 `0x51` 一次拿到 Q0–Q3，读 `0x7F` 一次拿全 6 个序列号寄存器。

8 个寄存器正好用满 18 字节负载（2 + 16），一个字节不剩。

> 本库曾把这个数写成 4，直到 2026-08-27 才在真机上纠正（`ray-292`）。**手册摘要
> §3.3 一直是对的**，这一条不属于上游资料缺陷（§9），是本库自己读错了。多出的 8
> 字节被 `unpack_from` 静默丢弃，而离线测试发现不了——构造帧的测试工具与被解码的
> 代码用的是同一个错误常量，两边一起错就一起「通过」。

## 4. 下行指令格式

固定 5 字节：

| 操作 | 字节序列 |
|---|---|
| 写寄存器 | `FF AA <reg> <valLow> <valHigh>` |
| 读寄存器 | `FF AA 27 <reg> 00` |
| 解锁 | `FF AA 69 88 B5`（写 `0x69` = `0xB588`） |
| 保存 | `FF AA 00 00 00`（写 `0x00` = `0x0000`） |

**写寄存器时序**：解锁 → 延时 ≈100 ms → 写目标寄存器 → 延时 ≈100 ms → 保存。
官方示例里这个时序是硬编码的；本库把它封装为一个原子操作，不暴露给调用方。

> ⚠ **官方 Python SDK 的缺陷**：`unlock()` / `save()` 调用了 async 函数却没有
> `await`，指令实际从未发出。照抄那份实现会得到「写了但没生效」。

### `save` 之后设备会忙一段时间（真机实测）

`FF AA 00 00 00` 发出后，设备写 flash 需要约 **300 ms**，期间对部分寄存器**回读出
中间状态**。实测：`save` 之后立刻读 `0x64` 电量寄存器，4/4 读到 0——而 `0x64` 是
电压 ×100，0 V 在一台正在发数据的设备上不可能。

零值回帧的形态值得注意：

```
零值帧: ['0x0000', '0x0000', '0x1147', '0x901A']
正常帧: ['0x018D', '0x0000', '0x1147', '0x901A']
```

`0x66` 与 `0x67` 与正常帧**完全相同**。这不是一帧垃圾或错位数据，而是一个结构完好
的回帧里单个寄存器读作 0，所以帧校验一类的手段抓不住它。

对照实验（同一设备、同一连接、每次写同一个值以排除「配置变了」）：

| 条件 | `0x64 == 0` |
|---|---|
| 解锁 + 写，**不保存** | 0 / 8 |
| 完整事务（含 `save`） | **4 / 4** |
| 完整事务后等 0.5 秒 | 0 / 4 |

逐轮测量恢复耗时：299 / 301 / 300 / 302 / 327 ms，分布极窄，像是固定的 flash 写入
时长。两台不同设备均复现。

**因此写事务在 `save` 之后必须等待再交还控制权**，且等待要在事务锁内——否则并发的
读能挤进这个窗口。本库的 `DEFAULT_SAVE_DELAY` 为 0.5 秒；`persist=False` 不写 flash
也就不需要等待。

## 5. 寄存器表

这张表**如实反映官方寄存器地址表的范围**，不只是本库开放的那些。「本库」那一列区分
三种状态：

| 记号 | 含义 |
|---|---|
| **开放** | 本库有具名入口（枚举成员 / `Telemetry` 方法 / `RegisterAccess` 的具名 setter） |
| **登记** | 本库知道它、写在这张表里，但没有具名入口——要用只能走通用 `read()` / `write()` |
| **保留** | 官方明确标注为「保留」。**不要写**，语义未定义 |

只写「本库开放的」会让下一个人以为官方表就这么大——而它比本库大得多，缺的那部分正是
下一次要不要补的候选。

### 5.2 官方地址表里没有、但本库开放的寄存器

标题**有意不写「设备确实有」**：前六个有协议文档的指令小节背书，`0x72` 有官方 SDK 代码
背书，而 `0x7F` **两份上游资料都查不到、真机四台次全零，它到底存不存在还没定论**（§0）。
把它们混成一句「设备确实有」，就是这一系列 Issue 要修的那种话。

| 地址 | 名称 | 读/写 | 本库 | 它的依据在哪 |
|---|---|---|---|---|
| `0x1F` | BANDWIDTH | R/W | **开放，七档全部登记**（`0x00`–`0x06`），**标称值一档都未实测**，见 §6.2 | 协议文档的「设置带宽」小节，给了完整寄存器规格（名称 / 地址 31 / R/W / **默认值 `0x0004`**）与七个取值，但**地址表里没有这一行** |
| `0x23` | MOUNTING | R/W | **开放** | 协议文档的「设置安装方向」小节：`0`=水平、`1`=垂直（**必须坐标轴的 Y 轴箭头朝上**，见 §5.5） |
| `0x24` | ALGORITHM | R/W | **开放** | 协议文档的「设置算法」小节：`0`=9 轴、`1`=6 轴（**编码与直觉相反**） |
| `0x27` | READADDR | W | **开放** | 协议文档的「读取寄存器值」小节。它是指令操作码，不是数据寄存器，本来也不该在地址表里 |
| `0x64` | POWER | R | **开放** | 协议文档的「读取电量」小节（指令 `FF AA 27 64 00` 与电压/电量对照表），地址表里没有 |

| `0x72` | MAGTYPE | R | **开放** | **只有官方 SDK**（`DipSensorMagHelper.java` 的分档换算），协议文档全文没有 |
| `0x7F`–`0x84` | SN | R | **开放**，但**这个寄存器是否存在于本型号尚未定论** | ⚠ **协议文档与官方 SDK 都查不到**，且真机四台次全零。`ray-309` scope 2 用实测定论，见 §0 与 §10 |

### 5.3 官方有指令、本库还没有入口的取值

这些**不是缺失的寄存器**，是已开放寄存器上本库还没接的取值。它们在 `ray-308` scope 3
补齐，这里先记账：

| 指令 | 官方取值 | 本库现状 |
|---|---|---|
| `FF AA 00 SAVE 00` | `0`=保存当前配置、`1`=**恢复默认配置并保存**、`0xFF`=**重启设备** | 只有 `0` |
| `FF AA 01 CALSW 00` | 另有 `0x04`=**设置 Z 轴角度归零**（需先切 6 轴算法才生效）、`0x08`=**设置角度参考**（发送后需再发保存指令） | 只有 `0x00`/`0x01`/`0x07` |
| `WT<14 字节名称>\r\n` | **设置蓝牙名称**。改名后需手动重启硬件或下发重启指令，再重新搜索 | 完全没有 |

### 5.4 ⚠ 官方寄存器地址表本身并不完整

这一条值得单独写下来，否则下一个人会以为**本库多写了东西**。

- 官方地址表**没有** `0x1F` BANDWIDTH、`0x23` MOUNTING、`0x24` ALGORITHM、`0x27`
  READADDR、`0x64` POWER、`0x69` KEY——但同一份文档的指令小节把它们全写清楚了，
  其中 `0x1F` 甚至给了完整的寄存器规格。**是那张表漏了，不是本库编的。**
- 官方地址表**也没有** `0x72` MAGTYPE 与 `0x7F` SN，而这两个的情况不同：`0x72` 有官方
  SDK 代码背书，`0x7F` **两份上游资料都查不到**（§0）。
- 表里本身还有大段跳号与一行省略号（见 §5.1 末尾）。

**所以「官方表里没有」不等于「设备没有」，也不等于「本库写错了」。** 判断一个地址可不
可信，要看它在**哪一份**资料的**哪一处**出现过，逐项出处见 §0。

### 5.5 `Mounting.VERTICAL` 有一条官方硬约束

协议文档的「设置安装方向」小节原文：

```
ORIENT：安装方向
0(0x00): 水平安装
1(0x01): 垂直安装（必须坐标轴的 Y 轴箭头朝上）
```

**括号里那句是硬约束，本库此前只写了「垂直安装」。** 装成垂直但 Y 轴没朝上，设备
**不会报错**——链路、速率、丢包全部正常，只有姿态解算的基准是错的，数据会一直偏。
这与写反 `0x23` 本身是同一类故障：在数据里看不出来。

代码侧的 docstring 在 `ray-308` scope 3 补（那里改的是公开契约）；这里先把事实记下。

### 5.6 设备自报 MAC（`0x66`–`0x68`）的字节序

三个寄存器按小端取出的 6 个字节是蓝牙地址的**空口顺序**（低位在前），显示时整体
倒过来。2026-08-27 两台 WT901BLE67 实测（`tools/probe_mac.py`）：

| 寄存器 `0x66`/`0x67`/`0x68` | 取出的 6 字节 | 显示 |
|---|---|---|
| `1147` `901A` `FD08` | `47 11 1A 90 08 FD` | `FD:08:90:1A:11:47` |
| `C931` `4F46` `F9B3` | `31 C9 46 4F B3 F9` | `F9:B3:4F:46:C9:31` |

手册只给了读 MAC 的指令 `FF AA 27 66 00`，**没给排布**。定这个顺序靠的是排除法：
四种可能的排布（寄存器正序/逆序 × 寄存器内高低字节两种）里，只有整体倒序让**两台**
设备都得到合法的蓝牙地址——倒序后首字节 `0xFD` / `0xF9` 的高 2 位都是 `11`，即 BLE
随机静态地址；另三种排布至少有一台落在「组播位为 1 的公有地址」（不存在）或「私有
地址」（会自己轮换，不可能固定写在寄存器里）。空口低位在前也正是 BLE 传地址的方式。

**这条结论没有被标签比对证实过**：设备标签上没印 MAC，macOS 只给 CoreBluetooth
UUID。在 Windows / Linux / Android 主机上看一眼同一台设备的 MAC 即可证实或推翻。

回读全零时本库抛异常而不是返回 `00:00:00:00:00:00`——序列号寄存器就出现过全零
（见 §10），MAC 若也如此，一个「所有设备都相同的稳定绑定键」会让两台设备安静地
互相冒充。

### 5.7 磁场换算依赖 `0x72`

结果单位 µT：

```
type 2 → ×0.15     type 3 → ×0.013    type 4 → ×0.058
type 5 → ×0.098    type 6 → ÷150      type 7 → ×0.020    其它 → 未知
```

本库在类型未知时返回 `value=None` 而不是原值——官方 Android SDK 原样返回未换算的
计数值，调用方会拿到一个**单位不明却看着正常**的数。

#### ⚠ 三份上游资料对磁场量纲的说法互相矛盾

本库此前只记了其中两份（把第三份写成「Python 示例陈旧」一句带过），那不足以描述实情。

| 资料 | 它说的换算 |
|---|---|
| **本型号官方协议文档** | 原始值单位**就是 mG**（`Hx=((HxH<<8)|HxL)`，并注明「和电脑上位机显示的单位不一样」），即 µT = raw × 0.1，**与 `0x72` 无关** |
| **官方 C# / Android SDK** | 按 `0x72` 分档，type 2 → ×0.15（本库采用） |
| **官方 Python 示例** | 写死 `raw / 120`（≈ ×0.00833） |

三者两两都对不上。要紧的是**第一份是本型号自己的协议文档**——出处比 SDK 更硬，却说
磁场换算根本不需要读 `0x72`。这不是「示例陈旧」能解释掉的，是一处真正的三方矛盾。

**本库暂时仍按 SDK 分档**，理由是它能解释 `0x72` 这个寄存器为什么存在：若原始值恒为
mG，那个寄存器就没有用处，而 C#、Android 两份独立实现都在读它。**但这只是权衡下的
暂定选择，不是结论**——本库没有实测过任何一档，无法判定谁对。

按本项目方针「官方资料互相矛盾处先立 Issue、以实测定论」，**这条要单独立项取证，
本节只负责如实记录矛盾，不做取舍**。

> ⚠ **判据修正（`ray-308` scope 2）**：scope 1 在这里写过「把设备放进已知场强（地磁
> 约 25–65 µT）读原始值，看哪一份换算能算出合理数量级」。**那个判据只分得开一份。**
>
> 协议文档自己给了例子：回帧 `55 71 3A 00 68 01 69 00 7A 00 …` 解出 `Hx=360`（mG）。
> 按 mG 读是 **36 µT**，按 SDK 的 type 2 ×0.15 读是 **54 µT**——**两个都落在地磁范围
> 内**，只有 Python 示例的 `/120`（3 µT）会被排除。
>
> 要分开前两份，需要一个**已知且可控**的场强，或者拿一台已标定的磁力计同点比对，而
> 不是「地磁量级合不合理」。这一点必须在立项时写进判据，否则会做一次分不出结果的
> 实验。

在那之前：拿 `magnetic_field_to_ut` 的返回值做**绝对场强**判断的调用方要知道它可能
整体差 1.5 倍或 18 倍；只用它做**相对变化或方向**的调用方不受影响。

## 6.2 带宽档位：七档全部登记，七个标称值全部没实测过

`Bandwidth` 登记 `0x1F` 的 `0x00`–`0x06` 全七档，**七个标称值载于本型号官方协议文档，
本库一个都没坐实**。这一节要说清两件事：那些数字的证据强度，以及为什么补全档位并不
违反 §6 立下的规矩。

> **出处更正（RAY-308）**：这一节此前写的是「七个标称值全部来自维特通用编码表」，
> 并据此打折扣。**那是把出处写低了一档**——协议文档自己就印着它们：
>
> ```
> 寄存器地址: 31 (0x1F)   读写方向: R/W   默认值: 0x0004
> BANDWIDTH[3:0]  0x00:256Hz  0x01:188Hz  0x02:98Hz  0x03:42Hz
>                 0x04:20Hz   0x05:10Hz   0x06:5Hz
> ```
>
> 七档与本库登记的完全一致。**证据强度上调，「本库未实测」不变**——出处更硬不等于
> 数字被量过，这两件事分开算。
>
> **官方默认值 `0x0004`（标称 20 Hz）** 本库此前也没记，见 §5.2 与下面那条对照。

| 编码 | 枚举 | 协议文档标称 | 本库实测 |
|---|---|---|---|
| `0x00` | `Bandwidth.HZ_256` | 256 Hz | 未实测（三档单调性取证之一） |
| `0x01` | `Bandwidth.HZ_188` | 188 Hz | 未实测，也未接受性验证 |
| `0x02` | `Bandwidth.HZ_98` | 98 Hz | 未实测，也未接受性验证 |
| `0x03` | `Bandwidth.HZ_42` | 42 Hz | 未实测（三档单调性取证之一） |
| `0x04` | `Bandwidth.HZ_20` | 20 Hz | 未实测（三档单调性取证之一） |
| `0x05` | `Bandwidth.HZ_10` | 10 Hz | 未实测，也未接受性验证 |
| `0x06` | `Bandwidth.HZ_5` | 5 Hz | 未实测，也未接受性验证 |

`0x07` 及以上仍然拒绝：白名单防的是**误**写（`0x02` 打成 `0x20`），这条理由与证据
强度无关，所以边界只是从「本库登记过的」挪到了「上游表列出的」，没有消失。

### 这与 §6 的「测不准的不进枚举」不矛盾

§6 排除 `0x0A` 的理由是**成员名在那里是一句断言**：`ReturnRate.HZ_100` 的意思是
「本库量到过 100 Hz」，所以把实测 99.29 Hz 的编码叫 `HZ_125` 会是一句假话。

`Bandwidth` 的成员名是**转述**：`HZ_98` 的意思只是「上游表把这个编码标为 98 Hz」。
转述必须标明出处，但不必先实测。两处的规矩其实是同一条——**名字不许说超出证据的话**——
只是断言与转述能说的话不一样。

代价是真实的：读代码的人可能不看文档就把 `HZ_98` 当成实测值。

此前这里给的理由是「同一张通用表在速率上已经被证伪过一次（§6 的 `0x0A`）」。
**RAY-308 之后那个类比不成立了**：被证伪的是通用表，而带宽这七个数出自协议文档；
协议文档的速率表根本没有 `0x0A`。理由换成下面三条，风险并没有因此消失：

1. **本库一档都没量过。** 出处硬不等于数字对。
2. **协议文档自己也把两列并成了一列**（见下），即使某一档被证实也只能对上其中一列。
3. **唯一一次尝试测量的结果与协议文档对不上**：标称 20 Hz 的 `0x04` 测出 10.9 Hz。
   那次自校验没过，所以结论是「这次没测出来」而不是「文档错了」——但它也不能算作
   对文档的支持。

接受这个代价是一个决定（RAY-304）：带宽滤波上位机自己能做，放在下位机只是实时性
更好；本库的职责是如实开放接口并标清证据强度，而不是替上层去核实芯片手册。
**要拿这些数字做采样率/抗混叠的设计决策，先自己测。**

在此之前只登记三档，需要 98 Hz 的调用方只能用通用 `write(0x1F, 0x02)` 绕过——那会
同时绕开这道白名单，比登记它更糟。

### 上游资料把两列并成了一列

MPU 类芯片的抗混叠滤波器对同一编码给**两个**略不同的截止频率（加速度一列、角速度
一列，典型如加速度 44 Hz / 角速度 42 Hz），而**协议文档与通用表都**每个编码只给一个
数。本库照抄，没有区分两列的依据。所以这些标称值即使将来被证实，也只能对上其中一列
——将来写实测判据时这一点必须先定下来。

### 官方默认值 `0x0004` 与实测读到的 `0x03` 对不上

协议文档给 `0x1F` 的默认值是 `0x0004`（标称 20 Hz）。而 RAY-298 取证时那台设备**连上
读回的是 `0x03`**。

这不是矛盾，是一条有用的事实：**那台设备被改过，不是出厂态。** 「读回什么就是出厂
什么」这个假设在本器件上不成立——本库取证用过的设备里已经确认有一台带着非出厂的
flash 配置。任何依赖出厂默认的推断都要先确认设备没被动过，而本库没有办法确认这件事。

（这台设备之前被本库自己的取证脚本写过 `0x03`，还是出厂就如此，已经分不开了——两种
情况对上面那个结论都成立，因为无论哪种，读回值都不能当作出厂值用。）

这也正是 `Register.MOUNTING` 那条坚持「不写就等于依赖设备残留配置」的原因：残留配置
不是假想风险，已经遇到过一次。

### 为什么带宽比速率难核实

原因在观测量：`ReturnRate` 逐档写入后**直接量样本速率**，观测量与被测量是同一个东西；
`0x1F` 改的是内部抗混叠滤波器的截止频率，它不改变样本速率，只改变样本内容的频率成分，
读寄存器只能读回自己刚写的编码。

2026-08-27 做过一次（`tools/probe_bandwidth.py`，`ray-298/bandwidth-42hz/acceptance/`）：
设备静置、回传速率 `0x0B`，对 `0x00`/`0x03`/`0x04` 三档各采 30 秒，用噪声底功率谱的
比值找 −3 dB 拐点。方法自带一条自校验——先拿标着 20 Hz 的 `0x04` 跑，看能不能读回
20 Hz。

| 档位 | −3 dB 估计（加速度 / 角速度） | 通带平台离散 |
|---|---|---|
| `0x04`（标称 20 Hz） | 10.9 / 10.7 Hz | 1.59 |
| `0x03`（标称 42 Hz） | 35.6 / 32.2 Hz | 1.20 |

**自校验没过**（判据要求 `0x04` 落在 15–32 Hz），所以同一次测出的 `0x03` 同样不算数。
成因有两种，那一轮分不开：要么方法无效，要么 `0x04` 在本型号固件上根本不是 20 Hz。

已知的一处方法缺陷：归一化假设 1–8 Hz 由传感器白噪声主导，而三档都原样放行的低频
成分（环境振动）会把归一化基准抬高，让所有拐点估计系统性左移。合成数据上这种污染
会把真值 20 Hz 读成 12.3 Hz。当时的门槛只查平台**平不平**（查到了，1.59 / 1.20），
没查平台的**绝对水平**——干净合成数据里该值约 0.27，接近 1 就说明基准无效。那一轮
没有打印这个量，所以事后无法从输出判断。

另一处：`0x04` 的曲线在 40 Hz 后压到 −13 dB 就平了，可用动态范围只有约 20:1。加速度
与角速度给出几乎一样的读数，说明限制因素是**共同的、在滤波器之后**的地板（ADC 量化 /
数字化 / 传输链路），不是预判的角速度量化底——换观测量解决不了。范围这么窄，−3 dB
拐点本就测不准。

**这轮确立的两件事**（不依赖上面的标定，因此仍然有效，但只覆盖那三档）：

1. 设备接受 `0x00` / `0x03` / `0x04` 三个编码，写入后照常出数，30 秒无丢样、无重同步。
2. 三档截止频率**单调有序**：全频段 `0x03` 的衰减严格小于 `0x04`（20 Hz 处 −1.4 dB
   vs −7.0 dB，50 Hz 处 −2.3 dB vs −13.1 dB），两者相对 `0x00` 都是衰减。

另四档（`0x01`/`0x02`/`0x05`/`0x06`）连这两件事都没测过，仅有的依据是上游表列出了它们。

另：取证那台设备连上时 flash 里存的就是 `BANDWIDTH=0x03`，说明该编码在本型号上是个
被实际用过的值。

### 2026-08-28 七档全测：噪声底法**测不出**绝对赫兹数（跨两台设备复现）

`ray-304/bandwidth-cutoff-probe`，判据于取证前预注册在 Issue 里。七档各采 30 秒
（参考档 `0x00` 另采一次，共 7 次），回传速率 `0x0B`，设备静置，**两台不同的
WT9011DCL-BT50 各跑一轮**。两轮全部链路干净：实测采样率 197.2–198.5 Hz，每档 22 段，
无丢样、无重同步。原始输出在 `ray-304/bandwidth-cutoff-probe/acceptance/`。

**结论：可用动态范围差了 26 dB，本方法测不出这七个截止频率。** 这是预注册判据列明的
三种完整交付之一，不是失败。

| 档位 | 标称 | 动态范围（设备一 / 设备二） |
|---|---|---|
| `0x06` | 5 Hz | 13.8 / 7.3 dB |
| `0x05` | 10 Hz | 7.7 / 6.0 dB |
| `0x04` | 20 Hz | 13.2 / 7.3 dB |
| `0x03` | 42 Hz | 7.9 / 6.3 dB |
| `0x02` | 98 Hz | 1.4 / 2.0 dB |
| `0x01` | 188 Hz | −0.4 / −0.3 dB |

判据要求 ≥40 dB。最好的一档只有 13.8 dB——**不是勉强没过，是差两个数量级**，重采改变
不了。`0x01` 的阻带地板是 1.07（比 1 还大），再次印证上一轮的诊断：地板是**共同的、
在滤波器之后**的东西（ADC 量化 / 数字化 / 链路固定底），加速度与角速度全程同步，
换观测量解决不了。

**七个标称赫兹数因此仍然一档都没有实测过。** 本轮没有坐实任何一个，也没有证伪任何
一个；输出里那些 −3 dB 估计**不可引用**。

#### 本轮确立的事（不依赖失败的判据）

1. 设备接受全部七个编码，逐档写入后照常出数，30 秒无丢样、无重同步。两台设备一致。
2. **响应形状确实跟着寄存器走**：`0x01`/`0x02` 全频段平坦（0 dB），`0x05`/`0x03` 滚降
   约 −8 dB，`0x06`/`0x04` 滚降约 −13~−14 dB。设备在响应 `0x1F`，这一点没有疑问。

#### 一个跨两台设备复现、但本库解释不了的现象

`0x06` 与 `0x04` 的曲线几乎重合，`0x05` 与 `0x03` 也几乎重合——偶数码配偶数码、奇数码
配奇数码，滚降深度成对（−13 dB 一对、−8 dB 一对）。两台设备都如此。

`0x02` 与 `0x01` 看起来也一样，但那**不算证据**：它们的拐点本就在 200 Hz 采样的奈奎斯特
（约 99 Hz）之外，无论真值多少都长得一样。

以 6–14 dB 的动态范围，−3 dB 估计不可信，所以这**只是观察，不是结论**。它可能意味着
七个编码在本型号固件上并不对应七个不同的滤波器，也可能只是本方法在低动态范围下的
假象。要定论需要换方法。

#### 一处判据缺陷，本轮暴露、未修

前置门槛「通带平台绝对水平 ≤0.40」在两轮真机数据上全部触发（实测 0.89–1.03），并
建议「重采」。**该门槛的标定不适用于真机**：它的干净基线 0.200–0.343 来自**白噪声**
合成——参考档 `0x00` 在 200 Hz 采样下把 100–256 Hz 折回带内，把参考谱的低频抬高了
几倍，比值因此偏低。真实传感器噪声是红噪声（1/f + 环境），高频没那么多东西可折，
参考档低频不被抬高，**平台接近 1 才是干净数据的正常值**。

审阅期复核证实了这个解释，并给出重标定的参数（`ray-304/bandwidth-cutoff-probe/review/`）。
同一套合成、只把噪声颜色注入到**器件滤波器之前**：

| 源噪声 | 10 Hz | 20 Hz | 42 Hz |
|---|---|---|---|
| 白（α=0） | 0.212 | 0.234 | 0.243 |
| 红（α=0.99） | 0.830 | 0.962 | 0.997 |
| 红（α=0.999） | 0.889 | 1.025 | 1.058 |
| **真机实测（两台，窄档）** | | **0.892–1.033** | |

白噪声重现原标定的 0.200–0.343，红噪声重现真机的 0.89–1.03。下一轮重标定用 α≈0.99–0.999。

（复核时第一次把红化加在合成**之后**，三位小数完全不变——同一线性滤波器同时作用于
候选与参考，相除时精确抵消。验证任何关于 R̂ 的假设，扰动必须只作用于单路，否则测的
是个空。）

数据本身也反驳了该门槛的理由（「R̂ 的形状不再由滤波器决定」）：形状清清楚楚随编码
变化，见上。

**本轮没有改这个门槛**——判据在取证前预注册，带着数据改判据正是要禁的事。结论也不
依赖它：动态范围那道门槛独立成立，两条路指向同一个结果。修正留给下一轮并需升需求
修订。

#### 这次失败在上真机之前就是可判定的

审阅期补跑发现：**动态范围那道门槛从来没有被合成标定评估过。** 门槛在取证前预注册了，
标定也建了，但标定只查平台绝对水平、平台离散、以及判据区间能否还原已知真值——从未拿
≥40 dB 去跑自己的合成数据。补跑之后：

| 档位 | 白噪声合成 | 红噪声合成 α=0.99 | 真机实测（两台） |
|---|---|---|---|
| `0x06` 5 Hz | 21.3 dB | 12.2 dB | 13.8 / 7.3 dB |
| `0x05` 10 Hz | 19.1 dB | 13.6 dB | 7.7 / 6.0 dB |
| `0x04` 20 Hz | 15.2 dB | 13.1 dB | 13.2 / 7.3 dB |
| `0x03` 42 Hz | 6.5 dB | 8.2 dB | 7.9 / 6.3 dB |

**连白噪声合成都从未接近过 40 dB。** 标定手上有全部所需信息，只是没去查；代价是真机
上白跑了两轮。结论不变——动态范围不足这个判定本身成立，只是它本可以早两轮得出。

`--self-test` 现在会评估并如实报出这一项（**门槛数值未改，改的是去评估它**），并明写
「不要再拿它去跑真机」。

#### 下一轮若还要测，得换方法

噪声底法的上限就在这里：它靠的是设备自身噪声，而噪声在滤波器之后又被一层共同的地板
压住。要拿到 40 dB 动态范围，得**主动激励**——给一个已知频率、幅度远高于地板的振动
输入，逐频点扫，测的就不再是噪声比而是传递函数。那需要振动台一类的器材，不是软件
能补的。

## 7. 寄存器读取是请求/响应事务

读寄存器不是「发了就有」。`FF AA 27 <reg> 00` 发出后模块回一帧 `0x55 0x71`，
必须比对「请求地址 == 回帧起始地址」才能采纳。官方 C# 的等待窗口默认 100 ms
（自动读暂停时 700 ms），读不到就重试或加长等待。

本库用「按寄存器地址匹配的 Future + 超时」实现关联，而非官方示例式的 sleep 轮询。

> ⚠ **并发读会导致永久挂起**（真机确认，见 `ray-177`）。一次回帧携带连续 8 个
> 寄存器，两个并发读若落在同一个 8 寄存器窗口内，回帧只有一份而等待者有两个。
> 窗口比原先认为的宽一倍，撞上的机会也就更大。本库把寄存器操作串行化。

## 8. 官方 SDK 的周期读取策略

C# 实现开后台线程持续补充非默认量：每轮读磁场 `0x3A` 与四元数 `0x51`；每 50 轮
读电量 `0x64` 与温度 `0x40`；每轮读时间 `0x30`；序列号、版本、磁场类型仅在为空时
读一次。

这些读取与 `0x61` 实时数据流抢同一条 BLE 链路，所以本库做成可配置、**默认关闭**。

**真机实测修正（2026-08-18）**：本库默认轮询配置（磁场/四元数 1 s，温度/电量
30 s）在 100 Hz 采集下对采样率的影响为 **0.1%–1.4%**（六次运行，20 秒窗口那次为
0.3%），resync 与 dropped 均为 0。设计文档早期写的「会明显挤占带宽」**言过其实**。
默认关闭仍然成立，但理由是「不用的人不该付费」以及代价随周期缩短线性增长，
不是「代价大」。

⚠ 实测的是**本库的默认配置**；官方 SDK 每轮都读，远比这激进，不能据此推断其代价。

## 9. 上游资料缺陷清单

一处汇总，实现时不得照抄：

1. **官方协议文档**：WY / WZ 公式复制粘贴错误，都写成了 `(WXH<<8)|WXL`。
2. **官方 Python SDK**：`unlock()` / `save()` 未 `await`，指令实际未发出。
3. **三份资料对磁场量纲互相矛盾**（不是某一份的缺陷，是一处未定论的分歧）：协议
   文档说原始值就是 mG（µT = raw × 0.1，与 `0x72` 无关）；C#/Android SDK 按 `0x72`
   分档（type 2 → ×0.15）；Python 示例写死 `/120`。详见 §5.7。
   **待单独立项以实测定论**，本库暂按 SDK 分档且明说这是暂定。
4. **官方 Android SDK**：磁场量纲类型未知时原样返回未换算值，得到单位不明的数。
5. **维特通用编码表**：把 `0x0A` 标为 125 Hz，而**本型号协议文档的速率表根本没有
   这个编码**；该固件实测 99.29 Hz。这是「通用表不适用于本型号」最直接的一例。
6. **协议文档与通用编码表都**：带宽每个编码只给一个截止频率，而 MPU 类芯片的抗混叠
   滤波器加速度与角速度各有一列（典型差 1–2 Hz）。那个数对应哪一列无从判断。
   （此前这条只记在通用编码表名下，而协议文档同样只给一列。）
7. **协议本身**：位移帧与实时数据帧共用 Flag `0x61` 且布局无法区分。
8. **协议文档与官方 SDK 对电量百分比给了两张不同的阶梯表**（21 档 5% 一级 vs 本库
   实现的 12 档），同一个原始值最多差 25 个百分点。详见 §5.8。**待单独立项以实测
   定论**，本库暂按 SDK 表且明说这是暂定。
9. **官方寄存器地址表本身不完整**：`0x1F` / `0x23` / `0x24` / `0x27` / `0x64` /
   `0x69` 都不在表里，却在同一份文档的指令小节里写得清清楚楚；表内还有大段跳号与
   一行省略号。详见 §5.4。

`endFieldCalibration` / `setReturnRate` / `setBandWidth`（仅 C# 有）/ `readReg` /
`writeReg` / `sendProtocolData`。以上全部在本库有对应入口。

SDK **一次都没碰过**的六组，本库有：`0x23` 安装方向、`0x24` 算法、`0x30`–`0x33`
芯片时间、`0x66` MAC、`0x7F` 序列号、`0x96` 输出内容。前五组有协议文档背书，`0x7F`
两边都没有（§0）。

### ⚠ 这次比对覆盖了什么、没覆盖什么

**已覆盖**：`Android_Java` 完整（86 个源文件）、iOS 协议层、Python SDK、C# 示例
`Form1.cs`。四份实现上交叉印证一致。

**未覆盖**：**Unity_C# 全部**、**Windows_C# 的 WitSdk 主体**、iOS 工程文件
（tarball 下载被截断）。

**所以「SDK 里没有的」这个结论的边界就到这里。** 下一个人不要把它当成一次完整比对
——补齐上面三块之后结论可能变。
