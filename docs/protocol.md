# WT9011DCL-BT50 协议参考

这份文档的目的是：**后续维护者不必重新考据官方资料。**

## 0. 来源与证据强度

本库有三份上游资料，**它们覆盖的范围并不相同**：

| 记号 | 指的是 |
|---|---|
| **协议文档** | 维特官方《蓝牙5.0通讯协议》，本型号自己的协议文档：<https://wit-motion.yuque.com/wumwnr/docs/ycui87fgg1mepk1u> |
| **官方 SDK** | `WITMOTION/WitBluetooth_BWT901BLE5_0`，钉住 commit `9efaab0fdd6a06dc807bf80402e58aa91b431c6f`（2024-09-19），见 §11 |
| **通用编码表** | 维特跨型号的编码对照表，**不是本型号文档**。它列出的 `0x0A` 速率编码本型号文档里根本没有（§6、§9 第 5 条）。RAY-308 之后本库不再拿它作为任何寄存器语义的依据，只在说明「它为什么不可信」时引用 |

> 因为下表有六组寄存器 SDK 一次都没碰过（`ray-309` 的 SDK 全量比对，见 §11）。它把

> 寄存器（`0x7F`）盖进了「已核实」里。逐项出处如下，**不再有整篇统一的核实声明**。

| `0x24` ALGORITHM | ✅ | ❌ | ✅ |
| `0x30`–`0x33` CHIPTIME | ✅ | ❌ | ✅ |
| `0x66` MAC（官方表作 `MAC0`/`MAC1`/`MAC2`） | ✅ | ❌ | ✅ |

**这张表只列 `ray-309` 逐项查过的七组**，不是全部寄存器。其余各项（`0x00` SAVE、
`0x01` CALSW、`0x03` RRATE、`0x1F` BANDWIDTH、`0x27` READADDR、`0x69` KEY、
`0x2E`–`0x2F` VERSION、`0x3A`–`0x3C` 磁场、`0x40` TEMP、`0x51`–`0x54` 四元数、
`0x64` POWER）**在官方 SDK 里都有代码实现**（§11 的读写全集；`0x2E`/`0x3A`/`0x51`
是 SDK 用的**起始地址**，一次应答回 8 个寄存器，其后各项随之覆盖，见 §3），本库据此
登记；它们
**是否也在协议文档的寄存器地址表里，本 scope 没有逐项核对**——没查就不打勾，这张表
里的空缺是「未核对」，不是「不存在」。

**`0x7F` 序列号两份上游资料都查不到。** 它进本库时没有留下出处，而它在真机上四台次
全为零（§10）。「这批器件没烧写序列号」与「本型号根本没有这个寄存器、读未定义地址
返回零」两种解释目前分不开，`ray-309` scope 2 用实测定论（读官方标为保留/未定义的
地址与它比对）。在那之前，**不要把 `0x7F` 当成已核实的寄存器**。

带「真机实测」标注的条目另有本仓库的实测数据支撑，证据路径见各节末尾。**真机实测与
上游资料冲突时以实测为准**——`0x0A` 就是这么被排除的：通用编码表标它 125 Hz，实测
99.29 Hz（§6、§9 第 5 条）。

（`0x71` 的寄存器个数不算这类冲突：手册摘要一直写着 8，是本库自己读成了 4，见 §3。）

⚠ **本文档记录的是设备与协议的事实，不是本库的 API。** API 见
[README](../README.md) 与 `wt901` 命名空间。

## 3. 上行帧格式

固定 **20 字节**：`0x55 | Flag | 18 字节负载`。**协议无校验和**——这与串口的
11 字节 0x55 协议不同，帧同步只能靠头字节与标志位约束。

### Flag `0x61` — 实时数据帧（默认持续上报）

负载为 9 个 int16（小端），顺序 AX AY AZ / WX WY WZ / Roll Pitch Yaw。
器件原始语义：

```
a[i]     = raw / 32768 * 16     (g)
w[i]     = raw / 32768 * 2000   (°/s)
angle[i] = raw / 32768 * 180    (°)
```

本库对外统一为 SI，换算集中在 `wt901.protocol.units` 一处。

> ⚠ **官方协议文档的复制粘贴错误**：WY 与 WZ 的公式都被误写为
> `(WXH<<8)|WXL`。三个轴各取各自的字节，不要照抄文档。

### Flag `0x61` — 位移帧（寄存器 `0x96` 置 1 后替代上表）

同样的 Flag，负载语义改为位移 XYZ / 位移速度 XYZ / 角度 XYZ，位移单位 mm。

> ⚠ **协议陷阱**：位移帧与实时数据帧**共用 Flag `0x61`，字节布局无法区分**。
> 解析必须以「当前已知的 `0x96` 配置状态」为上下文。本库的选择是拒绝而非猜测：
> `OutputMode` 非 `MOTION` 时 `samples()` 直接抛 `ConfigurationError`。

### Flag `0x71` — 寄存器回读帧

由主动读寄存器指令触发。`byte[2..3]` 是起始寄存器地址（小端），`byte[4..19]` 是
从该地址起**连续 8 个**寄存器值（int16 小端）。所以读 `0x3A` 一次拿到 HX/HY/HZ，
读 `0x51` 一次拿到 Q0–Q3，读 `0x7F` 一次拿全 6 个序列号寄存器。

8 个寄存器正好用满 18 字节负载（2 + 16），一个字节不剩。

> 本库曾把这个数写成 4，直到 2026-08-27 才在真机上纠正（`ray-292`）。**手册摘要
> §3.3 一直是对的**，这一条不属于上游资料缺陷（§9），是本库自己读错了。多出的 8
> 字节被 `unpack_from` 静默丢弃，而离线测试发现不了——构造帧的测试工具与被解码的
> 代码用的是同一个错误常量，两边一起错就一起「通过」。

## 4. 下行指令格式

固定 5 字节：

| 操作 | 字节序列 |
|---|---|
| 写寄存器 | `FF AA <reg> <valLow> <valHigh>` |
| 读寄存器 | `FF AA 27 <reg> 00` |
| 解锁 | `FF AA 69 88 B5`（写 `0x69` = `0xB588`） |
| 保存 | `FF AA 00 00 00`（写 `0x00` = `0x0000`） |

**写寄存器时序**：解锁 → 延时 ≈100 ms → 写目标寄存器 → 延时 ≈100 ms → 保存。
官方示例里这个时序是硬编码的；本库把它封装为一个原子操作，不暴露给调用方。

> ⚠ **官方 Python SDK 的缺陷**：`unlock()` / `save()` 调用了 async 函数却没有
> `await`，指令实际从未发出。照抄那份实现会得到「写了但没生效」。

### `save` 之后设备会忙一段时间（真机实测）

`FF AA 00 00 00` 发出后，设备写 flash 需要约 **300 ms**，期间对部分寄存器**回读出
中间状态**。实测：`save` 之后立刻读 `0x64` 电量寄存器，4/4 读到 0——而 `0x64` 是
电压 ×100，0 V 在一台正在发数据的设备上不可能。

零值回帧的形态值得注意：

```
零值帧: ['0x0000', '0x0000', '0x1147', '0x901A']
正常帧: ['0x018D', '0x0000', '0x1147', '0x901A']
```

`0x66` 与 `0x67` 与正常帧**完全相同**。这不是一帧垃圾或错位数据，而是一个结构完好
的回帧里单个寄存器读作 0，所以帧校验一类的手段抓不住它。

对照实验（同一设备、同一连接、每次写同一个值以排除「配置变了」）：

| 条件 | `0x64 == 0` |
|---|---|
| 解锁 + 写，**不保存** | 0 / 8 |
| 完整事务（含 `save`） | **4 / 4** |
| 完整事务后等 0.5 秒 | 0 / 4 |

逐轮测量恢复耗时：299 / 301 / 300 / 302 / 327 ms，分布极窄，像是固定的 flash 写入
时长。两台不同设备均复现。

**因此写事务在 `save` 之后必须等待再交还控制权**，且等待要在事务锁内——否则并发的
读能挤进这个窗口。本库的 `DEFAULT_SAVE_DELAY` 为 0.5 秒；`persist=False` 不写 flash
也就不需要等待。

## 5. 寄存器表

| 地址 | 名称 | 读/写 | 说明 |
|---|---|---|---|
| `0x00` | SAVE | W | 写 `0x0000` 保存配置 |
| `0x01` | CALSW | W | `0x0001` 加计校准；`0x0007` 开始磁场校准；`0x0000` 结束校准 |
| `0x03` | RRATE | R/W | 回传速率，见 §6 |
| `0x1F` | BANDWIDTH | R/W | 抗混叠带宽。**官方默认值 `0x0004`**（标称 20 Hz）。开放 `0x00`=256 Hz、`0x03`=42 Hz、`0x04`=20 Hz，**标称值均未实测**，见 §6.2 |
| `0x23` | MOUNTING | R/W | 安装方向。`0`=水平、`1`=垂直。**出厂默认值未核实** |
| `0x24` | ALGORITHM | R/W | 姿态解算算法。`0`=9 轴、`1`=6 轴（**编码与直觉相反**）|
| `0x27` | READADDR | W | 读寄存器指令操作码 |
| `0x2E`–`0x2F` | VERSION | R | 两寄存器拼 uint32；最高位为 1 时按 17/6/8 位拆 `主.次.修订` |
| `0x30`–`0x33` | CHIPTIME | R | 年月 / 日时 / 分秒 / 毫秒，各寄存器高低字节各承载一个字段 |
| `0x3A`–`0x3C` | HX/HY/HZ | R | 磁场三轴原始值 |
| `0x40` | TEMP | R | 温度 = raw / 100（°C） |
| `0x51`–`0x54` | Q0–Q3 | R | 四元数 = raw / 32768 |
| `0x64` | POWER | R | 电池原始值（≈电压 ×100），按阶梯映射百分比 |
| `0x66`–`0x68` | MAC | R | 设备自报蓝牙地址，6 字节**空口序**（显示时整体倒序），见下 |
| `0x69` | KEY | W | 写 `0xB588` 解锁 |
| `0x72` | MAGTYPE | R | **磁场量纲类型**，磁场换算必须先读它 |
| `0x7F`–`0x84` | SN | R | 序列号，6 个寄存器 = 12 字节 ASCII。⚠ **协议文档与官方 SDK 都查不到这个地址**，且真机四台次全零，见 §0 |
| `0x96` | — | W | 置 1 时输出切换为位移/位移速度/角度 |

**这张表逐项的出处（协议文档 / 官方 SDK / 两者皆无）见 §0**，各项并不相同。

### 设备自报 MAC（`0x66`–`0x68`）的字节序

三个寄存器按小端取出的 6 个字节是蓝牙地址的**空口顺序**（低位在前），显示时整体
倒过来。2026-08-27 两台 WT901BLE67 实测（`tools/probe_mac.py`）：

| 寄存器 `0x66`/`0x67`/`0x68` | 取出的 6 字节 | 显示 |
|---|---|---|
| `1147` `901A` `FD08` | `47 11 1A 90 08 FD` | `FD:08:90:1A:11:47` |
| `C931` `4F46` `F9B3` | `31 C9 46 4F B3 F9` | `F9:B3:4F:46:C9:31` |

手册只给了读 MAC 的指令 `FF AA 27 66 00`，**没给排布**。定这个顺序靠的是排除法：
四种可能的排布（寄存器正序/逆序 × 寄存器内高低字节两种）里，只有整体倒序让**两台**
设备都得到合法的蓝牙地址——倒序后首字节 `0xFD` / `0xF9` 的高 2 位都是 `11`，即 BLE
随机静态地址；另三种排布至少有一台落在「组播位为 1 的公有地址」（不存在）或「私有
地址」（会自己轮换，不可能固定写在寄存器里）。空口低位在前也正是 BLE 传地址的方式。

**这条结论没有被标签比对证实过**：设备标签上没印 MAC，macOS 只给 CoreBluetooth
UUID。在 Windows / Linux / Android 主机上看一眼同一台设备的 MAC 即可证实或推翻。

回读全零时本库抛异常而不是返回 `00:00:00:00:00:00`——序列号寄存器就出现过全零
（见 §10），MAC 若也如此，一个「所有设备都相同的稳定绑定键」会让两台设备安静地
互相冒充。

### 磁场换算依赖 `0x72`

结果单位 µT：

```
type 2 → ×0.15     type 3 → ×0.013    type 4 → ×0.058
type 5 → ×0.098    type 6 → ÷150      type 7 → ×0.020    其它 → 未知
```

本库在类型未知时返回 `value=None` 而不是原值——官方 Android SDK 原样返回未换算的
计数值，调用方会拿到一个**单位不明却看着正常**的数。

#### ⚠ 三份上游资料对磁场量纲的说法互相矛盾

本库此前只记了其中两份（把第三份写成「Python 示例陈旧」一句带过），那不足以描述实情。

| 资料 | 它说的换算 |
|---|---|
| **本型号官方协议文档** | 原始值单位**就是 mG**（`Hx=((HxH<<8)|HxL)`，并注明「和电脑上位机显示的单位不一样」），即 µT = raw × 0.1，**与 `0x72` 无关** |
| **官方 C# / Android SDK** | 按 `0x72` 分档，type 2 → ×0.15（本库采用） |
| **官方 Python 示例** | 写死 `raw / 120`（≈ ×0.00833） |

三者两两都对不上。要紧的是**第一份是本型号自己的协议文档**——出处比 SDK 更硬，却说
磁场换算根本不需要读 `0x72`。这不是「示例陈旧」能解释掉的，是一处真正的三方矛盾。

**本库暂时仍按 SDK 分档**，理由是它能解释 `0x72` 这个寄存器为什么存在：若原始值恒为
mG，那个寄存器就没有用处，而 C#、Android 两份独立实现都在读它。**但这只是权衡下的
暂定选择，不是结论**——本库没有实测过任何一档，无法判定谁对。

按本项目方针「官方资料互相矛盾处先立 Issue、以实测定论」，**这条要单独立项取证，
本节只负责如实记录矛盾，不做取舍**。判定它只需一次实测：把设备放进已知场强（例如
地磁，约 25–65 µT）里读原始值，看哪一份换算能算出合理数量级。

在那之前：拿 `magnetic_field_to_ut` 的返回值做**绝对场强**判断的调用方要知道它可能
整体差 1.5 倍或 18 倍；只用它做**相对变化或方向**的调用方不受影响。

## 6. 速率档位（真机逐档实测）

2026-08-18 于 WT901BLE67 逐档写入并测量实际样本速率，工具 `tools/probe_rates.py`
（全程 `persist=False`，不写 flash）。证据：`ray-171/register-access/acceptance/`。

| 编码 | 实测 | 标称 | 偏差 | 本库 |
|---|---|---|---|---|
| `0x06` | 10.05 Hz | 10 | 0.5% | `ReturnRate.HZ_10`（出厂默认） |
| `0x07` | 19.86 Hz | 20 | 0.7% | `ReturnRate.HZ_20` |
| `0x08` | 49.45 Hz | 50 | 1.1% | `ReturnRate.HZ_50` |
| `0x09` | 99.26 Hz | 100 | 0.7% | `ReturnRate.HZ_100` |
| `0x0A` | 99.29 Hz | 125 | **20.6%** | **未开放** |
| `0x0B` | 198.43 Hz | 200 | 0.8% | `ReturnRate.HZ_200` |

> ⚠ **`0x0A` 在本型号官方表里根本不存在。** 协议文档的速率表是 `0x09:100Hz`、
> `0x0B:200Hz`，**没有 `0x0A`**。「`0x0A` = 125 Hz」出自维特跨型号的通用编码表，
> 本型号文档从未这么说（RAY-308）。
>
> 实测与之一致：写入 `0x0A` 测出 99.29 Hz，与 `0x09` 几乎相同。这不是 BLE 带宽
> 不足——同一次探测里 `0x0B` 跑到 198 Hz（≈3970 B/s）。
>
> 所以排除它的理由有两条而不是一条：**本型号官方表没定义这个编码**，实测又证实了
> 一遍。上面那张表的「标称 125 / 偏差 20.6%」是拿通用表的数算的，留着是为了说明
> 那个数从哪来，**不是说本型号标称 125 Hz**。
>
> 这条印证的是「不得凭**通用**编码表补全本型号的寄存器语义」——通用表有一个编码
> 本型号压根没有，而它在纸面上看不出任何异常。**测不准的不进枚举；本型号没定义的
> 更不进。**

低于 10 Hz 的档位（`0x01`–`0x05`）未探测。`BANDWIDTH` **七档一档都未逐档探测**，
它与本节是两种不同的东西，见 §6.2——那一节也解释了为什么给带宽补全档位，与上面
这条「不得凭通用编码表补全寄存器语义」并不矛盾（简短版：带宽那七个数出自**本型号
协议文档**，不是通用表）。

### 6.1 多设备并发下的速率（真机实测）

上表是**单设备**逐档写入测出来的。并发时链路要分给多台设备，速率能不能保持是另一
个问题，必须单独测。证据：`ray-174/multi-device-replay/acceptance/`（100 Hz）与
`ray-189/dual-device-200hz/acceptance/`（200 Hz）。

| 条件 | 时长 | 两路实测 | `dropped` / `resync` / `reconnects` |
|---|---|---|---|
| 双设备 `HZ_100` | 10 分钟 | 99.4 / 99.3 Hz | 0 / 0 / 0 |
| 双设备 `HZ_200` | 15 分钟 | 198.7 / 198.6 Hz | 0 / 0 / 0 |

双设备 200 Hz 与单设备的 198.43 Hz 没有可测量的差别。合流侧共 357543 个样本
（397.3 Hz，约 7.9 kB/s），`out_of_order` 为 0 且与逐样本独立核对一致。
**两台并发不分带宽。**

> 三台及以上未测。macOS / CoreBluetooth 之外的平台也未在真机上跑过任何一档——
> Linux 与 Windows 的代码路径存在，但从未有真机数据。

设备一连上就开始推送，而第二台还在扫描/连接/配置期间，先连上的那台没有消费者，
样本队列（`DEFAULT_QUEUE_SIZE` = 1024，200 Hz 下约 5.2 秒）填满即丢。这些丢弃发生
在采集开始之前，判读时必须与采集期的丢弃分开——实测中出现过 496 个。

## 6.2 带宽档位：七档全部登记，七个标称值全部没实测过

`Bandwidth` 登记 `0x1F` 的 `0x00`–`0x06` 全七档，**七个标称值载于本型号官方协议文档，
本库一个都没坐实**。这一节要说清两件事：那些数字的证据强度，以及为什么补全档位并不
违反 §6 立下的规矩。

> **出处更正（RAY-308）**：这一节此前写的是「七个标称值全部来自维特通用编码表」，
> 并据此打折扣。**那是把出处写低了一档**——协议文档自己就印着它们：
>
> ```
> 寄存器地址: 31 (0x1F)   读写方向: R/W   默认值: 0x0004
> BANDWIDTH[3:0]  0x00:256Hz  0x01:188Hz  0x02:98Hz  0x03:42Hz
>                 0x04:20Hz   0x05:10Hz   0x06:5Hz
> ```
>
> 七档与本库登记的完全一致。**证据强度上调，「本库未实测」不变**——出处更硬不等于
> 数字被量过，这两件事分开算。
>
> **官方默认值 `0x0004`（标称 20 Hz）** 本库此前也没记，见 §5 与下面那条对照。

| 编码 | 枚举 | 上游表标称 | 本库实测 |
|---|---|---|---|
| `0x00` | `Bandwidth.HZ_256` | 256 Hz | 未实测（三档单调性取证之一） |
| `0x01` | `Bandwidth.HZ_188` | 188 Hz | 未实测，也未接受性验证 |
| `0x02` | `Bandwidth.HZ_98` | 98 Hz | 未实测，也未接受性验证 |
| `0x03` | `Bandwidth.HZ_42` | 42 Hz | 未实测（三档单调性取证之一） |
| `0x04` | `Bandwidth.HZ_20` | 20 Hz | 未实测（三档单调性取证之一） |
| `0x05` | `Bandwidth.HZ_10` | 10 Hz | 未实测，也未接受性验证 |
| `0x06` | `Bandwidth.HZ_5` | 5 Hz | 未实测，也未接受性验证 |

`0x07` 及以上仍然拒绝：白名单防的是**误**写（`0x02` 打成 `0x20`），这条理由与证据
强度无关，所以边界只是从「本库登记过的」挪到了「上游表列出的」，没有消失。

### 这与 §6 的「测不准的不进枚举」不矛盾

§6 排除 `0x0A` 的理由是**成员名在那里是一句断言**：`ReturnRate.HZ_100` 的意思是
「本库量到过 100 Hz」，所以把实测 99.29 Hz 的编码叫 `HZ_125` 会是一句假话。

`Bandwidth` 的成员名是**转述**：`HZ_98` 的意思只是「上游表把这个编码标为 98 Hz」。
转述必须标明出处，但不必先实测。两处的规矩其实是同一条——**名字不许说超出证据的话**——
只是断言与转述能说的话不一样。

代价是真实的：读代码的人可能不看文档就把 `HZ_98` 当成实测值。

此前这里给的理由是「同一张通用表在速率上已经被证伪过一次（§6 的 `0x0A`）」。
**RAY-308 之后那个类比不成立了**：被证伪的是通用表，而带宽这七个数出自协议文档；
协议文档的速率表根本没有 `0x0A`。理由换成下面三条，风险并没有因此消失：

1. **本库一档都没量过。** 出处硬不等于数字对。
2. **协议文档自己也把两列并成了一列**（见下），即使某一档被证实也只能对上其中一列。
3. **唯一一次尝试测量的结果与协议文档对不上**：标称 20 Hz 的 `0x04` 测出 10.9 Hz。
   那次自校验没过，所以结论是「这次没测出来」而不是「文档错了」——但它也不能算作
   对文档的支持。

接受这个代价是一个决定（RAY-304）：带宽滤波上位机自己能做，放在下位机只是实时性
更好；本库的职责是如实开放接口并标清证据强度，而不是替上层去核实芯片手册。
**要拿这些数字做采样率/抗混叠的设计决策，先自己测。**

在此之前只登记三档，需要 98 Hz 的调用方只能用通用 `write(0x1F, 0x02)` 绕过——那会
同时绕开这道白名单，比登记它更糟。

### 上游资料把两列并成了一列

MPU 类芯片的抗混叠滤波器对同一编码给**两个**略不同的截止频率（加速度一列、角速度
一列，典型如加速度 44 Hz / 角速度 42 Hz），而**协议文档与通用表都**每个编码只给一个
数。本库照抄，没有区分两列的依据。所以这些标称值即使将来被证实，也只能对上其中一列
——将来写实测判据时这一点必须先定下来。

### 官方默认值 `0x0004` 与实测读到的 `0x03` 对不上

协议文档给 `0x1F` 的默认值是 `0x0004`（标称 20 Hz）。而 RAY-298 取证时那台设备**连上
读回的是 `0x03`**。

这不是矛盾，是一条有用的事实：**那台设备被改过，不是出厂态。** 「读回什么就是出厂
什么」这个假设在本器件上不成立——同一批设备里已经确认有一台带着非出厂的 flash 配置。
任何依赖出厂默认的推断都要先确认设备没被动过，而本库没有办法确认这件事。

这也正是 `Register.MOUNTING` 那条坚持「不写就等于依赖设备残留配置」的原因：残留配置
不是假想风险，已经遇到过一次。

### 为什么带宽比速率难核实

原因在观测量：`ReturnRate` 逐档写入后**直接量样本速率**，观测量与被测量是同一个东西；
`0x1F` 改的是内部抗混叠滤波器的截止频率，它不改变样本速率，只改变样本内容的频率成分，
读寄存器只能读回自己刚写的编码。

2026-08-27 做过一次（`tools/probe_bandwidth.py`，`ray-298/bandwidth-42hz/acceptance/`）：
设备静置、回传速率 `0x0B`，对 `0x00`/`0x03`/`0x04` 三档各采 30 秒，用噪声底功率谱的
比值找 −3 dB 拐点。方法自带一条自校验——先拿标着 20 Hz 的 `0x04` 跑，看能不能读回
20 Hz。

| 档位 | −3 dB 估计（加速度 / 角速度） | 通带平台离散 |
|---|---|---|
| `0x04`（标称 20 Hz） | 10.9 / 10.7 Hz | 1.59 |
| `0x03`（标称 42 Hz） | 35.6 / 32.2 Hz | 1.20 |

**自校验没过**（判据要求 `0x04` 落在 15–32 Hz），所以同一次测出的 `0x03` 同样不算数。
成因有两种，那一轮分不开：要么方法无效，要么 `0x04` 在本型号固件上根本不是 20 Hz。

已知的一处方法缺陷：归一化假设 1–8 Hz 由传感器白噪声主导，而三档都原样放行的低频
成分（环境振动）会把归一化基准抬高，让所有拐点估计系统性左移。合成数据上这种污染
会把真值 20 Hz 读成 12.3 Hz。当时的门槛只查平台**平不平**（查到了，1.59 / 1.20），
没查平台的**绝对水平**——干净合成数据里该值约 0.27，接近 1 就说明基准无效。那一轮
没有打印这个量，所以事后无法从输出判断。

另一处：`0x04` 的曲线在 40 Hz 后压到 −13 dB 就平了，可用动态范围只有约 20:1。加速度
与角速度给出几乎一样的读数，说明限制因素是**共同的、在滤波器之后**的地板（ADC 量化 /
数字化 / 传输链路），不是预判的角速度量化底——换观测量解决不了。范围这么窄，−3 dB
拐点本就测不准。

**这轮确立的两件事**（不依赖上面的标定，因此仍然有效，但只覆盖那三档）：

1. 设备接受 `0x00` / `0x03` / `0x04` 三个编码，写入后照常出数，30 秒无丢样、无重同步。
2. 三档截止频率**单调有序**：全频段 `0x03` 的衰减严格小于 `0x04`（20 Hz 处 −1.4 dB
   vs −7.0 dB，50 Hz 处 −2.3 dB vs −13.1 dB），两者相对 `0x00` 都是衰减。

另四档（`0x01`/`0x02`/`0x05`/`0x06`）连这两件事都没测过，仅有的依据是上游表列出了它们。

另：取证那台设备连上时 flash 里存的就是 `BANDWIDTH=0x03`，说明该编码在本型号上是个
被实际用过的值。

### 将来若要实测

七档齐备之后有一件三档时做不到的事：`0x05`(10 Hz) / `0x06`(5 Hz) 的拐点远低于出问题
的区间，其上方有充足频谱确立阻带，可以当**方法的锚点**用。于是「方法无效」与「标签
不对」这两种成因可以分开——低端还原准而 42 Hz 不准，问题就在动态范围；低端就还原不准，
方法本身无效。上一轮拿 `0x04` 单点赌自校验，失败时两者分不开，正是卡住的地方。

## 7. 寄存器读取是请求/响应事务

读寄存器不是「发了就有」。`FF AA 27 <reg> 00` 发出后模块回一帧 `0x55 0x71`，
必须比对「请求地址 == 回帧起始地址」才能采纳。官方 C# 的等待窗口默认 100 ms
（自动读暂停时 700 ms），读不到就重试或加长等待。

本库用「按寄存器地址匹配的 Future + 超时」实现关联，而非官方示例式的 sleep 轮询。

> ⚠ **并发读会导致永久挂起**（真机确认，见 `ray-177`）。一次回帧携带连续 8 个
> 寄存器，两个并发读若落在同一个 8 寄存器窗口内，回帧只有一份而等待者有两个。
> 窗口比原先认为的宽一倍，撞上的机会也就更大。本库把寄存器操作串行化。

## 8. 官方 SDK 的周期读取策略

C# 实现开后台线程持续补充非默认量：每轮读磁场 `0x3A` 与四元数 `0x51`；每 50 轮
读电量 `0x64` 与温度 `0x40`；每轮读时间 `0x30`；序列号、版本、磁场类型仅在为空时
读一次。

这些读取与 `0x61` 实时数据流抢同一条 BLE 链路，所以本库做成可配置、**默认关闭**。

**真机实测修正（2026-08-18）**：本库默认轮询配置（磁场/四元数 1 s，温度/电量
30 s）在 100 Hz 采集下对采样率的影响为 **0.1%–1.4%**（六次运行，20 秒窗口那次为
0.3%），resync 与 dropped 均为 0。设计文档早期写的「会明显挤占带宽」**言过其实**。
默认关闭仍然成立，但理由是「不用的人不该付费」以及代价随周期缩短线性增长，
不是「代价大」。

⚠ 实测的是**本库的默认配置**；官方 SDK 每轮都读，远比这激进，不能据此推断其代价。

## 9. 上游资料缺陷清单

一处汇总，实现时不得照抄：

1. **官方协议文档**：WY / WZ 公式复制粘贴错误，都写成了 `(WXH<<8)|WXL`。
2. **官方 Python SDK**：`unlock()` / `save()` 未 `await`，指令实际未发出。
3. **三份资料对磁场量纲互相矛盾**（不是某一份的缺陷，是一处未定论的分歧）：协议
   文档说原始值就是 mG（µT = raw × 0.1，与 `0x72` 无关）；C#/Android SDK 按 `0x72`
   分档（type 2 → ×0.15）；Python 示例写死 `/120`。详见 §5「磁场换算依赖 `0x72`」。
   **待单独立项以实测定论**，本库暂按 SDK 分档且明说这是暂定。
4. **官方 Android SDK**：磁场量纲类型未知时原样返回未换算值，得到单位不明的数。
5. **维特通用编码表**：把 `0x0A` 标为 125 Hz，而**本型号协议文档的速率表根本没有
   这个编码**；该固件实测 99.29 Hz。这是「通用表不适用于本型号」最直接的一例。
6. **协议文档与通用编码表都**：带宽每个编码只给一个截止频率，而 MPU 类芯片的抗混叠
   滤波器加速度与角速度各有一列（典型差 1–2 Hz）。那个数对应哪一列无从判断。
   （此前这条只记在通用编码表名下，而协议文档同样只给一列。）
7. **协议本身**：位移帧与实时数据帧共用 Flag `0x61` 且布局无法区分。

> 比对来定论。**这条不删**：现象本身经过实测，删掉会丢掉真实数据；改的只是「它意味
> 着什么」这一层。
